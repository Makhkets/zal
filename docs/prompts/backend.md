# Промпт для ИИ бэкендера

Ты работаешь с jasperBLCK в ветке backend репозитория ZAL. Makhkets делает интерфейс, 3D, дизайн и презентацию. У команды 5 часов, цель — максимально закрыть 31 балл из PDF и сделать реальную оплату через Platega по СБП с выдачей электронного билета.

Прочитай AGENTS.md, docs/plan.md, docs/criteria.md, docs/api.md, contracts/openapi.json, docs/architecture.md, docs/platega.md и docs/deployment.md. Контракт уже отдан фронтендеру: не меняй названия полей и состояний молча.

Твоя зона apps/api: FastAPI, sqlite3, httpx, схемы, миграция/seed, атомарная бронь, заказы, Platega, callback, сверка статусов, билеты, HTTPS и постоянное хранение. Фронтенд не редактируй, кроме согласованных интеграционных правок.

Сначала B1: каталог двух кинотеатров, будущие сеансы, геометрия Hall из общих fixtures, цены и состояния мест из БД. На фронте нельзя зашивать каталог и цены. Повторный seed не стирает покупки. Новый зал добавляется данными, не копией роутов.

Затем B2–B5: один заказ на одно место, гостевой email, Idempotency-Key, атомарная бронь, Platega SBP, подтверждение, один билет. В PostgreSQL не мигрировать без необходимости — используем один процесс и SQLite на постоянном диске.

Ключи получить у Makhkets отдельно и положить в apps/api/.env:

~~~dotenv
PLATEGA_MERCHANT_ID=<из приватного файла владельца>
PLATEGA_API_KEY=<из приватного файла владельца>
PLATEGA_BASE_URL=https://app.platega.io
PAYMENT_PROVIDER=platega
PUBLIC_APP_URL=https://<публичный-домен>
ORDER_TOKEN_SECRET=<постоянный-случайный-секрет>
~~~

Ключ/merchant уже прошли read-only проверку, результат docs/platega-check.json. Значения намеренно отсутствуют в этом отслеживаемом Git промпте. Не проси вставлять их в Issue, не выводи в терминал и не добавляй в код.

Точная схема интеграции и ссылки — docs/platega.md. Используй официальный https://docs.platega.io/: POST /transaction/process, paymentMethod=2, заголовки X-MerchantId/X-Secret; GET /transaction/{id}; публичный POST callback на нашем сервере. Передавай email покупателя в metadata.user_email. Сумма от БД, в провайдер — рубли через Decimal; payload связывает платёж с существующим заказом.

Важные инварианты:

- До подтверждённого платежа билет не существует, место held.
- Return URL лишь открывает проверку статуса; never trust клиентское paid.
- Секрет callback сравнивается безопасно, transactionId/сумма/валюта/заказ сверяются с серверными данными и GET провайдера.
- Callback и polling вызывают один атомарный обработчик. UNIQUE(order_id) для билета, уникальная активная бронь места.
- Дубли/параллельные события/старые статусы не выпускают второй билет и не откатывают paid.
- Таймаут создания платежа не ведёт к повторному POST вслепую.
- Таймер не освобождает бронь без сверки с провайдером.
- Спор/возврат меняет доступность билета; неизвестные статусы не превращаются в paid.
- Рестарт сохраняет заказы, токены, бронь, события и билеты.

Билет: случайный token, данные сеанса и места, QR на публичную проверку, статусы valid/suspended/revoked. GET приватного заказа требует Bearer access_token; публичная проверка не раскрывает email. Печать делает фронт, отдельный PDF необязателен.

С первого часа подними HTTPS и доступный callback. Не перезаписывай callback общего мерчанта, пока не выяснишь, не обслуживает ли он другие проекты. При необходимости маршрутизируй по transactionId/payload.

Запиши зависимости и команды запуска, создай тесты гонки двух покупателей, повторной оплаты/события, несовпадения суммы, отсутствия секрета, отказа провайдера и восстановления из SQLite. Тесты используют фейковый provider adapter, не реальные списания.

Реальный платёж проверяется человеком отдельно после готовности HTTPS. До этого честно отмечай, какие стадии работают. Через 45 минут отдай фронтендеру API чтения, к 2 часам — первый сквозной путь. PR небольшими этапами, merge через main.
